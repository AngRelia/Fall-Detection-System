# ICM42688 + MMC5603 九轴工程 —— 代码审查与结合毕设的改造清单

> 审查对象：`D:\STM32Project\ICM42688+MMC5603 9 axis gyroscope`
> 目标：与《可穿戴跌倒与疲劳检测系统》（江彬锋毕设）结合
> 审查方式：静态代码审查 + 工程构建产物（`.map` / `.htm` / `.sct`）核对 + 数据手册逐条比对
> 结论：**工程能跑、算法配置与数据手册基本吻合，但有 5 个必须修的问题，其中 2 个会让新增功能直接失效。**

---

## 0. 结论速览

| 级别 | 问题 | 影响 |
|---|---|---|
| 🔴 P0 | `HAL_UARTEx_RxEventCallback()` 从未实现 | 串口**接收**通道完全失效，上位机下行命令全丢 |
| 🔴 P0 | USART2 实际波特率 9600，代码按 115200 打印 | 节点间链路/采集通道一上来就是错的，且**串口打印阻塞主循环** |
| 🔴 P0 | `Mahony_Init(100.0f)` 硬编码 100 Hz，真实融合周期不可控 | 姿态角在旋转时严重偏差 → 直接废掉要求（1） |
| 🟠 P1 | `imu_update_count` 是 `uint8_t` 且中断/主循环非原子读写 | 丢采样、静默数据缺口 → 毁掉 TinyML 训练数据 |
| 🟠 P1 | 磁力计 ~9 Hz 读取后被整批融合复用，且读取时阻塞 10 ms | 九轴融合实际退化为"滞后修正"，Yaw 振荡 |
| 🟡 P2 | 加速度零偏校准是空操作；batched drain 固定 dt；SPI 分两次读 | 精度/时序健壮性问题 |
| 🟡 P2 | `vTaskDelay` 式靠时基的架构：主循环里 OLED/printf/Flash 全阻塞 | 想上 200 Hz 融合 + TinyML 必须重构为中断/DMA 驱动 |

**总体判断：现有代码作为"能跑的演示"是合格的，但它的采样与融合是"主循环里同步阻塞"的架构，直接叠加 TinyML 与疲劳判定会立刻撞到天花板。建议按第 4 节的顺序改造，第 1～3 节的问题必须先修。**

## 1. 先说做对的部分（别乱改）

这些地方我逐条对着数据手册核过，是对的，集成时保留：

| 项 | 核对结果 |
|---|---|
| GYRO_CONFIG0 = `0x06` | ✅ ±2000 dps（FS=000，bit7:5）+ ODR 1 kHz（0x6）。与 `GYRO_SENSITIVITY = 2000/32768` 完全一致 |
| ACCEL_CONFIG0 = `0x06` | ✅ ±16 g（FS=000）+ ODR 1 kHz。与 `ACC_SENSITIVITY = 16/32768` 一致 |
| PWR_MGMT0 = `0x0F` | ✅ Gyro=11(LN)、Accel=11(LN)，1 kHz ODR 下 LN 模式合法 |
| SPI Mode 3 配置 | ✅ 手册 `DEVICE_CONFIG.SPI_MODE` 明确写 **"0: Mode 0 and Mode 3 (default)"**，Mode 3 合法 |
| SPI 18 MHz（PCLK2 72 MHz ÷ 4） | ✅ 手册 `fSPC` max = **24 MHz**，24 MHz 下 `tLOW/tHIGH` 各 min **17 ns**，18 MHz 半周期 27.8 ns，满足 |
| SPI `tSU.CS` min 39 ns | ✅ 软件 CS 拉低到首字节进 DR 有 5～7 条指令（~100 ns @72 MHz），满足 |
| MMC5603 灵敏度 `16384 LSB/G` | ✅ 手册"0.0625 mG per LSB" → 1/0.0000625 = **16384**，正确；20-bit 无符号，零点 2^19 = **524288**，正确 |
| MMC5603 20-bit 拼接公式 | ✅ 与手册 `Xout0=Xout[19:12] / Xout1=Xout[11:4] / Xout2=Xout[3:0]` 一致（代码读 0x00–0x08 连续 9 字节，Xout2/Yout2/Zout2 恰好是 raw[6]/[7]/[8]） |
| MMC5603 0x1A = ODR、0x1B = CTRL0、`Auto_SR_en` = bit5 | ✅ 与手册寄存器表一致；`0x20` 置 Auto_SR_en、`0x01\|0x20` 单次测量保持 Auto_SR_en，写法正确 |
| Flash 页 `0x0800FC00` | ✅ F103C8 是 64 KB / 1 KB 页，这是最后一页；scatter 文件 load region `0x08000000 + 0x00010000`，应用占用 40.14 KB，**不冲突** |
| TIM2 1 kHz（PSC 719 / ARR 999） | ✅ APB1=36 MHz，定时器时钟 72 MHz（APB1 分频≠1 故 ×2），72 MHz/720/1000 = **1 kHz**，正确 |
| 栈/堆 | ✅ Stack 0x400 (1 KB) + Heap 0x200 (512 B)，RAM 4.80 KB / 20 KB |
| 仪器构建产物 | ✅ `Total RO = 40952 (39.99 kB)`、`Total RW = 4920 (4.80 kB)`，与方案 §1.3 记录的 **40.14 KB / 4.80 KB** 一致，仍余 **≈23.9 KB Flash / ≈15.2 KB RAM** |

> 唯一"理论越界但仍能跑"的是 SPI 18 MHz 对**自制 PCB**的余量问题（见 §3.6），不是报错项。

## 2. 🔴 P0：必须修，否则新功能直接失效

### 2.1 `HAL_UARTEx_RxEventCallback()` 从未实现 —— 接收通道是死的

`Serial.c` 里有 `Serial2_DMA_RxEvent()`，它的注释写着"由 main.c 中的 `HAL_UARTEx_RxEventCallback` 调用"，但**全工程搜不到任何一处定义这个回调**。

构建产物直接证实了这一点：

```
ICM42688+MMC5603 9 axis gyroscope.map:
  Line 2106:  Removing serial.o(i.Serial2_DMA_RxEvent), (88 bytes).
  Line 2588:  i.HAL_UARTEx_RxEventCallback  0x080040de  Section 0  stm32f1xx_hal_uart.o
  Line 3125:  HAL_UARTEx_RxEventCallback    0x080040df  Thumb Code 2  stm32f1xx_hal_uart.o
```

链接器把 `Serial2_DMA_RxEvent` 当**死代码删掉了**（88 字节），而 `HAL_UARTEx_RxEventCallback` 只有 HAL 里那个 **2 字节的 `__weak` 空实现**。也就是说：

- `Serial2_Init()` 启动了 `HAL_UARTEx_ReceiveToIdle_DMA()`，DMA 在搬运数据；
- 但 **IDLE / 半满 / 全满事件到了之后没有任何用户代码处理** → `Serial2_RxPacket` 永远空，`Serial2_RxFlag` 永远是 0；
- DMA 是 NORMAL 模式且从不重启 → 收满 500 字节后**永久停止接收**。

**后果**：任何"上位机 → MCU"的下行链路（模式切换、实验打标、参数下发、取消按钮远程复位）全部无效。毕设里的"自采数据按键打标"如果走串口下行，会直接不工作。

**修法**（加到 `main.c` 的 `/* USER CODE BEGIN 4 */` 区块）：

```c
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    if (huart->Instance == USART2)
    {
        Serial2_DMA_RxEvent(Size);                             /* 解析已到达的字节 */
        HAL_UARTEx_ReceiveToIdle_DMA(&huart2, RxBuffer, RX_BUFFER_SIZE); /* 重新武装 */
    }
}
```

注意：`RxBuffer` 和 `RX_BUFFER_SIZE` 目前是 `Serial.c` 里的非 static 全局，跨文件 `extern` 可用，但更干净的做法是在 `Serial.h` 里导出它们、或在 `Serial.c` 里封装一个 `Serial2_ReArm()`。

### 2.2 USART2 波特率：初始化 9600，代码按 115200 打印

```c
/* Core/Src/usart.c */
huart2.Init.BaudRate = 9600;     // ← CubeMX 生成值

/* 方案与计划 §1.2 / §10 也确认："USART2 = 9600 bps（需改 115200）" */
```

但 `Serial.c` 基于 DMA 编写、`main.c` 每轮打印 `"roll:%.2f,pitch:%.2f,yaw:%.2f\r\n"`（约 34 字节）——按 9600 bps 算**一帧要 35 ms**，而主循环周期目标只有 10 ms。于是 `Serial2_WaitTxFinish()` 的忙等会**每轮阻塞 20～30 ms**。

这两件事叠加的后果很严重：

1. 如果你按方案把节点间链路按 115200 设计，而这里没改，**收到的全是乱码**；
2. 如果你把终端设成 9600，**能看，但姿态刷新率被串口拖垮**；
3. 更糟的是——`imu_update_count` 在中断里以 1 kHz 累加，主循环被串口卡住 30 ms 后，内层 `while (imu_update_count > 0)` 会**一股脑排空 30 个样本**，每个都用固定 dt。这就是 §2.3 的灾难来源。

**修法**：`usart.c` 里 `9600` → `115200`，同时 `.ioc` 里的值也要改（否则下次 CubeMX 重新生成又被打回 9600）。并且**不要再在主循环里同步 printf**，改成环形缓冲 + DMA 发送（见 §4）。

### 2.3 `Mahony_Init(100.0f)` 硬编码 100 Hz，而真实融合周期完全不可控

`main.c`：

```c
Mahony_Init(100.0f);        // invSampleFreq = 1/100 = 0.01 s
```

`MahonyAHRS.c` 里 `invSampleFreq` 是**唯一的积分步长**，同时用于：

```c
gx *= (0.5f * invSampleFreq);      // 四元数积分
integralFBx += twoKi * halfex * invSampleFreq;   // 积分反馈
```

但真实融合调用频率是多少？**不确定，而且每轮都在变**：

| 耗时来源 | 量级 |
|---|---|
| `MMC5603_ReadData_Single()` 里的 `HAL_Delay(10)` | **10 ms（硬阻塞）** |
| `OLED_Update()` @ 10 Hz | 数 ms（软件 I2C 整屏刷） |
| `Serial2_Printf()` @ 10 Hz @ 9600 bps | **~35 ms（硬阻塞）** |
| `Get_Acc` + `Get_Gyro` 各 6 字节 SPI | ~10 µs，可忽略 |

所以真实周期在 **10 ms 到 50 ms 之间抖动**，而代码告诉 Mahony 是固定的 10 ms。当主循环被串口卡住 30 ms 时，它会在几毫秒内排空 30 个样本，**每个都按 dt=10 ms 积分** → 相当于把 10 ms 的物理时间当成 300 ms 来积分。

**后果**：设备不动时姿态看着正常（加速度计在拉回来），**一旦旋转，角度严重超前/偏差**，Yaw 基本不可用。这正好命中要求（1）"实时计算姿态角"，是答辩最容易被现场验证穿帮的点。

**修法**（三选一，推荐 A）：

**A. 让采样频率真的是常数（推荐）**
把融合搬进定时器中断，或者用"一次中断一个样本"的严格节拍：

```c
/* TIM2 1 kHz ISR */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM2) {
        /* 只置标志，不做 I2C —— 严格 1 个样本 1 次 */
        imu_sample_pending = 1;
    } else if (htim->Instance == TIM3) {
        Key_Tick();
    }
}

/* 主循环：绝不排空积压，只处理最新一个 */
if (imu_sample_pending) {
    imu_sample_pending = 0;
    Get_Acc_Gyro_ICM42688_Burst();       /* 见 §3.3，一次 12 字节 */
    MahonyAHRSupdateIMU(gx*DEG2RAD, gy*DEG2RAD, gz*DEG2RAD, ax, ay, az);
    Mahony_computeAngles();
}
Mahony_Init(1000.0f);   /* 现在它是诚实的 */
```

彻底去掉 `imu_update_count` 排空循环，把降采样做成"每 N 次融合取一次显示/输出"。

**B. 把实测周期喂给 Mahony（退而求其次）**
用 `HAL_GetTick()` 测两次调用之间的真实间隔，动态更新 `invSampleFreq`。注意 `HAL_Delay` 只有 1 ms 分辨率，周期 <10 ms 时误差很大。

**C. 至少先把磁力计和串口移出关键路径**，把周期压到相对稳定，再固定 `Mahony_Init()` 的值。

## 3. 🟠 P1 / 🟡 P2：正确性与健壮性

### 3.1 `imu_update_count` 是 `uint8_t`，且读写非原子 —— 会静默丢数据

```c
volatile uint8_t imu_update_count = 0;    // main.c

/* ISR（1 kHz） */
imu_update_count++;

/* 主循环 */
while (imu_update_count > 0) {
    imu_update_count--;      // ← 读-改-写，非原子
    ...
}
```

两个问题：

1. **溢出**：1 kHz 递增，`uint8_t` 只够 **256 ms**。主循环任何一次超过 256 ms 的停顿（OLED 刷屏 + 串口 + Flash 擦写）都会让它绕回，计数语义彻底丢失。
2. **竞态**：`imu_update_count--` 编译成 `LDRB / SUB / STRB` 三条指令。若 TIM2 中断恰好落在 `LDRB` 与 `STRB` 之间，那次 `++` 就被覆盖丢失。1 kHz 下这不是偶发，是**持续性的少量丢采样**。

对姿态影响不大，但对**要求（2）的 TinyML 是致命的**——你的 2 s @ 100 Hz 窗口需要 200 个连续样本，静默缺口会让训练集和推理输入的节拍不真实，标签与波形对不齐。

**修法**：换成 §2.3 的"单样本标志"或 `__disable_irq()` 保护的临界区，或干脆用环形缓冲 + DMA 采集（见 §4）。

### 3.2 磁力计以 ~9 Hz 读取，却被整批融合复用

`main.c` 的循环结构：

```c
while (1) {
    ...
    if (mag_enabled == 1) {
        MMC5603_ReadData_Single(&hi2c2);   // ← 外层循环，每次 ~10 ms 阻塞
        /* 计算 calib_x/y/z */
    }

    while (imu_update_count > 0) {          // ← 内层排空 N 个样本
        Get_Acc_ICM42688();
        Get_Gyro_ICM42688();
        Mahony_update(..., -calib_y, calib_x, calib_z);   // 同一个 mag 值用 N 次
    }
}
```

外层循环因为 `HAL_Delay(10)` 大约 9～10 Hz，内层可能一次跑几十次。于是**同一组磁力计值被反复喂给九轴融合**，而陀螺仪数据每次都是新的。这不只是"磁力计带宽低"那么简单——Mahony 的磁力计项是**修正项**，用陈旧值连续修正会让 Yaw 出现周期性回拉/抖动，而且修正强度是 `Kp = 2×100 = 200`（`mag_enabled` 时），非常强。

另外，`MMC5603_ReadData_Single()` 里的 `HAL_Delay(10)` 是**硬阻塞**，它直接把主循环周期锁死在 ≥10 ms，也是 §2.3 的元凶之一。

**修法**（推荐）：
- 磁力计改为**连续模式**（`CTRL2.Cmm_en` + `Cmm_freq_en`），用 `Status1` 的测量完成位或定时器按 ~50 Hz 读取，**绝不在融合路径里 `HAL_Delay`**；
- 或者按方案 §3(1) 的结论——**穿戴场景主方案就用六轴**，把 MMC5603 降级为论文里的"九轴对比实验"。这既符合你的方案（穿戴磁干扰大），也能把 `HAL_Delay(10)` 从关键路径彻底拿掉，一举解决 §2.3 的周期抖动。

### 3.3 加速度计与陀螺仪分成两次 SPI 事务读 —— 有采样间偏斜

```c
void Get_Acc_ICM42688(void)   { ICM_ReadRegs(ICM42688_ACCEL_DATA_X1, buf, 6); ... }  // 0x1F
void Get_Gyro_ICM42688(void)  { ICM_ReadRegs(ICM42688_GYRO_DATA_X1,  buf, 6); ... }  // 0x25
```

手册确认 `ACCEL_DATA_X1 (0x1F)` 到 `GYRO_DATA_Z0 (0x2A)` 是**连续**的，并且这些寄存器标记为 `SYNCR`（同步读）。当前写法做了两次 CS 拉低/拉高、两次独立的寄存器读，六轴数据来自**不同采样点**。

对跌倒检测这恰恰是要命的地方：跌倒特征是"自由落体（加速度模值骤降）紧接冲击（模值骤升）"，这两个事件间隔可能只有几十毫秒。加速度与陀螺不同步会让"冲击时的角速度"对不上，"自由落体 + 旋转"的复合特征被削弱。这也是方案 §3(2) 里阈值预筛 `|a| > 2.5 g` 与 `|Δ角度| > 60°/s` 需要联合判断的前提。

**修法**：一次读 12 字节（0x1F 起），顺带省掉一半 SPI 开销：

```c
void Get_AccGyro_ICM42688(void)
{
    uint8_t buf[12];
    ICM_ReadRegs(ICM42688_ACCEL_DATA_X1, buf, 12);   /* 0x1F..0x2A 连续 */
    icm42688_acc_x = (int16_t)((buf[0]<<8)|buf[1]) * ACC_SENSITIVITY  - acc_offset_x;
    icm42688_acc_y = (int16_t)((buf[2]<<8)|buf[3]) * ACC_SENSITIVITY  - acc_offset_y;
    icm42688_acc_z = (int16_t)((buf[4]<<8)|buf[5]) * ACC_SENSITIVITY  - acc_offset_z;
    icm42688_gyro_x = (int16_t)((buf[6]<<8)|buf[7]) * GYRO_SENSITIVITY - gyro_offset_x;
    icm42688_gyro_y = (int16_t)((buf[8]<<8)|buf[9]) * GYRO_SENSITIVITY - gyro_offset_y;
    icm42688_gyro_z = (int16_t)((buf[10]<<8)|buf[11]) * GYRO_SENSITIVITY - gyro_offset_z;
}
```

### 3.4 加速度零偏校准是空操作

```c
float acc_offset_x = 0.00f; // 填入你平放时读到的 AccX
float acc_offset_y = 0.00f; // 填入你平放时读到的 AccY
float acc_offset_z = 0.00f; // 填入 (平放时读到的 AccZ - 1.0f)
...
icm42688_acc_x -= acc_offset_x;   // 永远是 -0
```

`IMU_Calibrate()` **只标定陀螺仪**（`gyro_offset_x/y/z`），加速度零偏靠人工填常数，且默认值全 0。后果：

- 每次上电陀螺零偏重算（500 样本 × `HAL_Delay(2)` ≈ 1 s 阻塞），但**加速度零偏从不更新**；
- 加速度零偏直接影响静态姿态角：`pitch = atan2(-ax, az)`、`roll = atan2(ay, az)`。例如 az 有 0.02 g 偏差，在水平附近就能带来 ≈1.1° 的系统误差，而且它**会作为"真实重力"持续骗过 Mahony 的加速度修正项**，让 Roll/Pitch 长期偏一个固定角。
- 另外 `gyro_offset_x/y/z` 和 `acc_offset_x/y/z` 在所有 `.h` 里都没有 `extern` 声明（虽然当前只有 `icm42688_driver.c` 用到，但这个耦合很脆）。

**修法**：把加速度零偏纳入 `IMU_Calibrate()`（静止时取均值，此时 `|a|` 应等于 1 g，用 `az_offset = az_mean - 1.0f`），并考虑把结果一起写进 Flash（现在 Flash 只存磁力计偏移 + 状态）。

### 3.5 `MahonyAHRSinit()` 从未被调用 —— 上电姿态从单位四元数起步

`MahonyAHRSinit(ax, ay, az, mx, my, mz)` 用一次静止测量初始化四元数，函数写得很完整（含磁力计的偏航初始化），但**全工程没有任何调用点**（已确认：只在 `MahonyAHRS.c` 定义、`MahonyAHRS.h` 声明）。

后果：`q = (1,0,0,0)` 起步，靠 `Kp` 慢慢收敛。六轴模式 `Kp = 2×0.5 = 1.0` 收敛较慢，上电后头几秒姿态不可信；如果上电时设备侧放/倾斜，还会有一段明显的瞬态。对"上电即用"的穿戴设备是体验问题，对论文里的实验数据是**前几秒必须丢弃**的麻烦。

**修法**：`IMU_Calibrate()` 之后、启动定时器之前，先读一次静止数据再调用：

```c
Get_AccGyro_ICM42688();
if (mag_enabled) MMC5603_ReadData_Single(&hi2c2);
Mahony_Init(1000.0f);   /* 与 §2.3 修正后的真实频率一致 */
MahonyAHRSinit(icm42688_acc_x, icm42688_acc_y, icm42688_acc_z,
               mag_enabled ? -mmc5603_data.calib_y : 0.0f,
               mag_enabled ?  mmc5603_data.calib_x : 0.0f,
               mag_enabled ?  mmc5603_data.calib_z : 0.0f);
```

### 3.6 SPI 速率对自制 PCB 的余量

18 MHz 在手册 24 MHz 上限内，Mode 3 合法，`tSU.CS` 也满足 —— **这不是报错项**。但你的 IMU 是**自制板**，走线长度、过孔、上下拉、探针焊接质量都会影响 4-wire SPI 的建立/保持余量。24 MHz 规格是在 TDK 评估板上characterize 的（手册 Table 6 Notes 明确写了 "as mounted on evaluation board or in sockets"）。另外 `GYRO_CONFIG_STATIC2 = 0xA0` 那句注释把 AAF 说成"Enable"了，实际 bit7=1 是 **disabling** AAF，注释与手册相反（功能上你确实想关 AAF，因为它支持不了 1 kHz ODR——所以是**注释错了，代码对了**）。

**建议**：先用 `SPI_BAUDRATEPRESCALER_8`（9 MHz）跑稳，确认 WHO_AM_I 连续 1000 次读取零错误、连续跑 30 min 不丢帧，再试着回到 18 MHz。顺手把 `Init_ICM42688()` 里的注释改成 "Disable AAF"。

## 4. 结合毕设的改造建议（按顺序做）

方案 §2.1 的双节点架构（节点 A 只做采样+融合，节点 B 做 TinyML）是对的，但**当前节点 A 的代码形态撑不起 200 Hz 融合 / 100 Hz 输出**。建议顺序：

**第 1 步：先让数据流可信（0.5 天）**
- 修 §2.1 的 UART 回调、§2.2 的波特率
- 修 §2.3 的采样节拍（改成"一次中断一个样本"），删掉 `imu_update_count` 排空循环
- 修 §3.3 的 12 字节 burst 读，修 §3.4 的加速度零偏，调用 §3.5 的 `MahonyAHRSinit()`

验收：串口稳定吐出 100 Hz 的 `roll/pitch/yaw`，连续 30 min 无缺口（用 PC 端 `serial_logger.py` 统计帧间隔标准差）。

**第 2 步：把阻塞全部移出主循环（1～2 天）**
- 磁力计：连续模式 + 非阻塞读取（或按方案决策直接降级为六轴比较实验）
- 串口：TX 改环形缓冲 + DMA，打印**不阻塞**
- OLED：降到最后刷，或只在空闲时刷
- Flash：`Mag_Calibrate()` 已经会停 TIM2，这点做得对，保留；但要确认 `Flash_Save_Settings()` 擦写期间（几十 ms）不会与新增的 TinyML 定时任务撞车

验收：主循环周期稳定，`while(1)` 里不再出现任何 `HAL_Delay`。

**第 3 步：帧协议 + 降采样输出（1 天）**
- 按方案 §2.2 实现 32 字节定长帧 + CRC-16/MODBUS。**注意当前 `Serial.c` 的 `Serial2_ProcessByte` 状态机在收到不含 `\r\n` 的垃圾流时，若 `pRxPacket2` 停在 499，随后 `Serial2_RxPacket[pRxPacket2] = '\0'` 会写到 `[499]`（下标恰好合法但字符串未截断）——建议把上限改成 498 并加超时复位，防止半帧卡死状态机。**
- 降采样：200 Hz 融合 → 100 Hz 输出（每 2 次融合发 1 帧）

**第 4 步：再上 TinyML / 疲劳判定（按方案 P2/P3）**

> ⚠️ 一个必须现在就写进论文的坑：**当前 `Serial2_RxPacket[500]` + `RxBuffer[500]` 已经吃掉 1 KB RAM**，而节点 B 的 TinyML 激活值预算约 4 KB（方案 §3(2)）。如果节点 A/B 都在 F103 上，注意别把这两个缓冲重复计入。节点 A 若只发不收，`RxBuffer` 可以缩到 64 字节甚至不启用。

## 5. 一并记录的"小问题清单"

| # | 位置 | 问题 |
|---|---|---|
| 1 | `main.c` `while (Init_ICM42688()!=0x47);` | 死循环无超时。传感器没插好 = 屏幕永远停在 "Init Sensor..."，无任何提示。建议加超时 + OLED 显示错误码 |
| 2 | `Init_ICM42688()` `ICM_WriteReg(DEVICE_CONFIG, 0x01)` | 软复位后只等 50 ms（手册要求 ≥1 ms，够），但**没有重新校验 WHO_AM_I** 就继续配置，且复位前的 CS_HIGH 时序无等待 |
| 3 | `Init_ICM42688()` 写 `INT_SOURCE0 = 0x08` | 使能了 INT1 上的 UI_DRDY 中断，但 INT1 引脚**没有引出到 MCU**，且从不读 `INT_STATUS` 清标志。属于无效配置（不致命，但建议删掉或明确注释"未使用"） |
| 4 | `MMC5603_CheckID()` | 只判 `0xFF` / `0x00`，不校验手册规定的 Product ID（`0x39`，期望 0x10）。读到任何其他值都当成功 |
| 5 | `MMC5603_ReadData_Single()` | `HAL_Delay(10)` 后直接读，**不查 `Status1` 的测量完成位**。BW=00 时手册测量时间 6.6 ms，10 ms 余量偏紧，且 `HAL_I2C_Mem_Read` 超时只有 10 ms。建议轮询 done 位 + 超时重试 |
| 6 | `MMC5603_ReadData_Single()` | 读失败时**静默保留旧值**（失败分支被注释掉了），旧磁力计数据会继续参与融合。建议置一个 `mag_valid` 标志并在融合里跳过修正 |
| 7 | `Mag_Calibrate()` | 硬球校准的 z 轴范围需要设备在三维空间翻转才有效；只水平旋转会得到错误的 `offset_z`。UI 提示只写了 "Rotate 8 shape!"，建议明确写"需翻转设备" |
| 8 | `Mahony_invSqrt()` | 做了两次 Newton 迭代（`invSqrt()` 只做一次）。快速平方根倒数在极端输入下数值稳定性一般，但这里输入是归一化的模值，实际影响很小——只是两处实现不一致，建议统一 |
| 9 | `icm42688_driver.h` | 定义了 Bank1/2 的寄存器宏（`GYRO_CONFIG_STATIC2` 等），但 `Init_ICM42688()` 里用的是裸地址 `0x0B/0x0C/0x03/0x04/0x05`。宏被定义了却没用，容易误读，建议统一 |
| 10 | `.ioc` 与 `usart.c` | CubeMX 重新生成会覆盖波特率等手工修改。**每次改外设后要同步改 `.ioc`**，否则下次生成代码把修复打回 |
| 11 | `key.c` | 长按识别是 2 s，方案 §3(5) 需要"取消按钮"的短按语义 + 20 s 取消窗口。当前 `Key_GetNum()` 短按只用于切页（`main.c` 里 `key==1` 切页、`key==2` 切 mag）。新增取消逻辑时要规划好按键复用，别和现有两套撞车 |

## 6. 关于"和毕设结合"的一个结构性提醒

`00-方案与计划.md` §1.2 说这个工程"几乎零改动"就能当传感器节点数据源。**从算法角度成立，从工程角度不成立。**

现在的固件是**同步阻塞式单线程**：读 SPI → 读 I2C（`HAL_Delay(10)`）→ 融合 → 刷 OLED → printf（可能再阻塞 35 ms）→ 下一轮。它没有"采样与处理解耦"，也没有任何时间戳/序号。

而方案 §2.2 的帧协议要求 `timestamp_ms` 和 `seq`，§3(3) 的疲劳判定要求"4 s 窗口方差 + 步态周期自相关"，§3(2) 的 TinyML 要求"2 s @ 100 Hz = 200 个严格等间隔样本"。**这些都以"等间隔、无缺口、带序号"为前提**——正是当前代码最缺的东西。

所以结合的正确姿势不是"复制过去加个 printf"，而是先做 §4 第 1～2 步的**采样架构改造**（把 `imu_update_count` 排空循环换成严格节拍 + 环形缓冲），改完之后：
- 要求（1）姿态角变得真的准；
- 要求（2）（3）所需的数据质量才有保障；
- 节点 B 才有干净、可复现的输入。

改造量大约 1.5～2.5 天，是后面 TinyML 和云端工作的地基。**建议优先做，别等到 P2 阶段。**

### 需要你在硬件上确认的两件事（静态审查无法判定）

1. **MMC5603 与 ICM-42688 的轴向对齐**：`main.c` 传给 Mahony 的是 `(-calib_y, calib_x, calib_z)`，这是一次显式轴重映射，说明两个芯片在自制板上贴装方向不同（很可能一个有 90° 旋转）。请确认这个映射在**右手系 + 旋转方向一致**的意义下正确——若方向反了，九轴修正会把 Yaw 往错误方向拉。验证方法：设备绕 z 轴顺时针转 90°，看 Yaw 是增加还是减小，再看磁力计三轴的变化是否符合该映射。
2. **18 MHz SPI 在自制板上的误码率**：抓 30 min 连续读，统计 WHO_AM_I 与数据寄存器是否出现异常值（如 `acc_z` 突然跳到量程边缘）。
