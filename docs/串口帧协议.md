# 串口帧协议（节点 A → 上位机）

> 适用工程：`D:\STM32Project\ICM42688+MMC5603 9 axis gyroscope`
> 链路：USART2 (PA2/PA3)，**115200 8N1**，DMA 收发
> 本文件是**唯一实现依据**；`00-方案与计划.md` §2.2 为早期草案，已被本文件取代。

---

## 0. 为什么是这个设计（先说结论，避免以后反复讨论）

**上位机做跌倒检测需要的是原始六轴，不是三个姿态角。**

依据：本工程已有的 TinyML 实现 [`tools/tinyml/features.py`](../tools/tinyml/features.py) 的输入约定就是
`win : (200, 6) —— 列序 ax, ay, az [g], gx, gy, gz [°/s]`，
29 维特征全部由这 6 通道现算，**全文未出现 roll/pitch/yaw**。

原因（跌倒检测的三个核心判据都靠原始量）：

| 判据 | 依靠 | 姿态角为何不行 |
|---|---|---|
| 自由落体 | `am_min`（合加速度→0） | 姿态角反映不出失重 |
| 冲击 | `am_max`、`dam_max`(jerk) | 姿态角是**低通输出**，瞬态被滤掉 |
| 跌倒后躺倒 | `tilt_deg` / `az_mean`（重力方向） | 用重力方向算更直接，且无万向锁 |

**姿态角的用途是另一条线**：满足毕设要求(1)「实时计算姿态角」、OLED 显示、人工核对、论文图表。

**所以一帧同时带两类数据**，各取所需 —— 而不是分成两种帧（那样会丢掉"原始量与姿态严格同一时刻"这个对齐优势）。

## 1. 物理层

| 项 | 值 |
|---|---|
| 接口 | USART2，PA2 = TX，PA3 = RX |
| 波特率 | **115200** |
| 数据格式 | 8 数据位 / 无校验 / 1 停止位（8N1） |
| 流控 | 无 |

## 2. 帧格式（定长 32 字节，小端）

### 2.1 完整布局

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 2 | `hdr[2]` | uint8 ×2 | **`hdr[0]=0xAA`, `hdr[1]=0x55`**（见下方说明，不要写成 uint16） |
| 2 | 1 | `type` | uint8 | `0x01` = IMU 数据帧（当前唯一类型） |
| 3 | 1 | `seq` | uint8 | 帧序号，0~255 回绕，用于丢帧统计 |
| 4 | 4 | `timestamp_ms` | uint32 | `HAL_GetTick()`，单位 ms，约 49.7 天回绕 |
| 8 | 6 | `acc_raw[3]` | int16 ×3 | 加速度**原始计数**，顺序 X,Y,Z |
| 14 | 6 | `gyro_raw[3]` | int16 ×3 | 角速度**原始计数**，顺序 X,Y,Z |
| 20 | 6 | `rpy[3]` | int16 ×3 | Roll/Pitch/Yaw，单位 **0.01°**，顺序 R,P,Y |
| 26 | 4 | `flags` | uint32 | 状态位，见 §3 |
| 30 | 2 | `crc16` | uint16 | CRC-16/MODBUS，**覆盖偏移 2~29 共 28 字节** |
| | **32** | | | |

### 2.2 为什么存「原始计数」而不是 mg / dps

`acc_raw` / `gyro_raw` 直接是 ICM-42688 的 16 位 ADC 输出（未经任何换算），
**零量化损失**。主机侧按灵敏度反算：

```
acc_g    = acc_raw  * (16.0   / 32768.0)      # ±16 g 满量程
gyro_dps = gyro_raw * (2000.0 / 32768.0)      # ±2000 dps 满量程
```

对应固件里的 `ACC_SENSITIVITY = 16.0f/32768.0f`、`GYRO_SENSITIVITY = 2000.0f/32768.0f`。

**量程与 int16 的余量**（这是关键）：

| 量 | 满量程 | 原始计数范围 | int16 余量 |
|---|---|---|---|
| 加速度 | ±16 g | ±32768 | 恰好用满（LSB = 0.49 mg） |
| 角速度 | ±2000 dps | ±32768 | 恰好用满（LSB = 0.061 dps） |

> ❗ **不要把 gyro 换成「0.1 dps」定点**：±2000 dps → ±20000，虽能放进 int16，
> 但**丢掉了原始分辨率**（0.1 比 0.061 粗），且白白引入舍入误差。存原始计数才是无损的。

**量化噪声是否够用**（以疲劳判定的 4 s 方差为例）：

- 加速度量化噪声 σ ≈ 0.49/√12 = **0.14 mg**
- 静态手持实际噪声 σ ≈ 7 mg（70 µg/√Hz × √100Hz）
- 方差相对误差 ≈ (0.14/7)² ≈ **0.04%** → **完全可忽略**

### 2.3 `rpy` 的语义（六轴 vs 九轴，论文必须写清）

> **已实现约定**：协议里的 `yaw` 与 OLED 显示的值**完全一致**，都是
> `yaw_display`。六轴时它是「相对**上电基准**的累计转角」，九轴时是磁北绝对方位。
> 上电基准在 `fusion_ready` 之后延迟 200 ms 捕获（此时融合已稳定）。
>
> ⚠️ **这里踩过一个坑，值得记录**：最初协议发的是原始 `yaw_mahony`，
> 而 OLED 显示的是减去上电基准后的值。结果**同一时刻两处相差一个基准量
> （实测差 52°）**。这在采集训练数据时很危险 —— 标签和特征会对不上。
> 现在两者共用 `yaw_display`，且计算被放在打包**之前**（顺序很关键）。

固件默认**上电六轴**。两种模式下 `rpy` 的可信度不同：

| 字段 | 六轴（默认） | 九轴（短按切换） |
|---|---|---|
| Roll / Pitch | ✅ 由重力观测，**绝对且准确** | ✅ 同 |
| **Yaw** | ⚠️ **仅相对转角**（陀螺积分 + 静止零偏修正），**会缓慢漂移**，上电起点任意 | ✅ 磁北绝对航向（需先做硬铁校准） |

**论文与答辩必须按上表表述** —— 六轴下的 Yaw 不能称为"绝对方位"。

数值范围：±180.00° → ±18000，int16 上限 32767，**余量充足**。

### 2.4 `timestamp_ms` 的用途

1. 主机侧**校验采样是否等间隔**（TinyML 的 29 维特征依赖固定 10 ms 间隔）
2. 与外部事件标记（按键打标、视频帧）对齐，便于给自采数据打标签

## 3. `flags` 状态位定义

| bit | 名称 | 含义 |
|---|---|---|
| 0 | `FUSION_READY` | 上电校准与 AHRS 初始化已完成 |
| 1 | `MAG_ENABLED` | 0 = 六轴，1 = 九轴 |
| 2 | `GYRO_AZ_DONE` | 静止自动零偏已完成首次学习 |
| 3 | `HEADING_SETTLING` | 处于上电收敛期（用大增益快速收敛） |
| 4 | `MAG_REF_VALID` | 磁力计参考航向有效（仅九轴） |
| 5 | `CALIB_OK` | 上电加速度校准残差 < 0.02 g |
| 6 | `MAG_INIT_ERR` | MMC5603 初始化失败（ID 读不到） |
| 7~31 | — | 预留 |

> 这几个位正是调试时最需要盯的（对应 OLED 第 3 页的 `AZ` / `ST` / `MagErr`），
> 发上来后**不用再看 OLED** 就能判断设备状态。

## 4. CRC-16/MODBUS

| 项 | 值 |
|---|---|
| 多项式 | `0x8005`（反射表示 `0xA001`） |
| 初值 | `0xFFFF` |
| 输入反射 | 是 |
| 输出反射 | 是 |
| 结果异或 | `0x0000` |
| 覆盖范围 | 偏移 **2~29**（**不含 header 与 crc 自身**） |

### 4.1 为什么 header 定义为两个独立字节，而不是 uint16

`0xAA55` 若声明成 **uint16 并按小端写出**，线上会是 `55 AA` —— 与惯例（先 `AA` 后 `55`）**相反**，
而且源码里写 `0x55AA` 才等价于线上 `AA 55`，极容易被后人改错。

所以**明确按两个字节定义**：

```c
#define PROTO_HDR0   0xAAu
#define PROTO_HDR1   0x55u
/* 打包: buf[0]=PROTO_HDR0; buf[1]=PROTO_HDR1; */
/* 解析: 直接比字节, 不要当 uint16 读 */
```

**为什么不覆盖 header**：让「帧同步」与「内容校验」两件事解耦；
header 只用于找帧头，内容正确性由 CRC 保证。

**为什么必须校验**：采集的训练数据一旦有静默位翻转，
坏样本会混进训练集污染模型 —— 这是无法事后察觉的。CRC 是刚需，不是可选项。

## 5. 发送架构（非阻塞）

```
Fusion_Task (TIM2 ISR, 200 Hz)
   └─ 只更新全局量（加速度/角速度/姿态/flags）

Proto_Task (主循环, 100 Hz 节拍)
   └─ 打包 32 字节 → Proto_Send()
                        └─ 写入 TX 环形缓冲（临界区保护）

DMA1_Channel7 TC 中断
   └─ HAL_UART_TxCpltCallback() → Proto_TxComplete()
                                   └─ 从环形缓冲取下一段继续发
```

**设计要点**：

| 要点 | 说明 |
|---|---|
| **绝不阻塞** | 环形缓冲满时**丢弃最旧帧并计数**（`tx_drop_cnt`），不忙等 |
| 临界区 | 入队时 `__disable_irq()` 前后各几十条指令，防止与 DMA TC 中断抢索引 |
| 缓冲大小 | 512 B（约 16 帧） |
| 速率解耦 | 打包 100 Hz，实际发送由 DMA 异步完成；主循环只需把帧塞进缓冲 |
| DMA 优先级 | 建议由 `LOW` 提到 `MEDIUM` |

**对比旧实现的问题**：原 `Serial2_Printf()` 会忙等 `HAL_UART_GetState` 直到发送完成，
在 100 Hz 下每次阻塞约 2.8 ms，必然拖慢主循环 —— 所以不能用它发数据帧。

## 6. 上位机解析要点

### 6.1 解析状态机

```
收到字节 → 找 0xAA → 下一个是 0x55 → 锁定帧头
        → 连续收满 32 字节
        → 校验 crc16（覆盖 [2..29]）
        → 校验通过: 解析字段; 通过 seq 检测丢帧
        → 校验失败: 丢弃, 重新找帧头
```

- **不要只靠 header 同步**：数据里可能恰好出现 `AA 55`，所以 CRC 才是真正的确认
- `seq` 每帧 +1，若跳变说明丢帧（结合 `timestamp_ms` 判断丢了几帧）

### 6.2 字段解析（Python 伪代码）

```python
import struct

LEN = 32

def parse(frame: bytes):
    if frame[0] != 0xAA or frame[1] != 0x55:   # 按字节比, 不要当 uint16
        return None
    typ, seq, ts = struct.unpack_from('<BBI', frame, 2)
    acc_raw  = struct.unpack_from('<3h', frame, 8)    # 原始计数
    gyro_raw = struct.unpack_from('<3h', frame, 14)
    rpy      = struct.unpack_from('<3h', frame, 20)   # 0.01 度
    flags,   = struct.unpack_from('<I',  frame, 26)
    crc,     = struct.unpack_from('<H',  frame, 30)
    if crc != crc16_modbus(frame[2:30]):
        return None
    acc  = [v * (16.0/32768.0)   for v in acc_raw]    # g
    gyro = [v * (2000.0/32768.0) for v in gyro_raw]   # dps
    return dict(seq=seq, t_ms=ts, acc=acc, gyro=gyro,
                roll=rpy[0]*0.01, pitch=rpy[1]*0.01, yaw=rpy[2]*0.01,
                flags=flags)
```

### 8.4 已知的次优之处（可接受，记录在案）

**实际帧率约 42 Hz，不是 100 Hz。**

原因：发送节拍挂在主循环上（每 2 圈发一帧），而主循环一轮约 12 ms
（九轴时磁力计读取占 10 ms）。

- 对**六轴**（当前默认）影响较小：没有磁力计读取，主循环更快，帧率会更高
- 上位机可用 `timestamp_ms` 校验真实间隔，必要时重采样
- 要做到**严格 100 Hz**，需把发送节拍改成独立定时器（例如 TIM4），
  这是独立改造，按需再做

**功耗/带宽目前很宽裕**：42 Hz × 32 B = 1.3 KB/s，仅占 115200 的 11%。
### 8.5 另一个必须记住的坑：DMA 不能直接从环形缓冲发送

**现象**：上位机抓到 5438 字节，**一帧都解不出来**。
统计显示 `0xAA` 出现 35 次、`0x55` 只出现 3 次
（若帧头正常，两者应各约 170 次）—— 帧头第 2 字节被大量吃掉。

**原因**：最初实现让 DMA 直接从环形缓冲取数据：

```c
HAL_UART_Transmit_DMA(&huart2, &tx_ring[tx_tail], n);   /* 读 tx_ring */
```

而 `tx_ring` **同时被主循环写入**。DMA 是一个字节一个字节往外挪的，
主循环却已经把新帧写进了同一块内存 → **正在发送的字节被就地覆盖**。
帧头与 CRC 被后续数据吃掉，剩下的载荷看起来像随机字节。

**修法**：DMA 只读一块**专用**缓冲 `tx_dma_buf[32]`，且用忙标志互锁：

```c
if (!proto_kick()) { stat_dropped++; return; }   /* 上一帧还在发, 本次丢弃 */
...打包到 pkt[]...
__disable_irq();
for (i = 0; i < 32; i++) tx_dma_buf[i] = pkt[i];  /* 只有这里写 */
__enable_irq();
```

`tx_dma_buf` 在整个发送期间不会被改写（`proto_kick` 返回 0 时直接丢弃本次数据），
所以从根本上没有竞争。长度只有 32 字节，拷贝开销可忽略。

> 教训：**任何被 DMA 读取的缓冲，都不能同时被 CPU 写入** ——
> 除非有严格的互锁。环形缓冲 + DMA 直发看起来很美，实际是竞争陷阱。
